1. 性能优化
================================================================================

问题 1.1: Admin接口加载全表数据，无分页（已优化：后台用户/景点/资讯/酒店/路线/社区内容列表改为分页；统计接口改为COUNT/SUM、TopN和近6个月窗口查询，避免全表加载）
------------------------------------------------------------------------
位置: AdminController.java
现象: findAll() 在多个端点中直接返回全部数据
  - /api/admin/stats 加载所有景点、用户、新闻
  - /api/admin/users 加载所有用户
  - /api/admin/spots 加载所有景点
  - /api/admin/news 加载所有新闻
  - /api/admin/hotels 加载所有酒店
风险: 数据量增长后接口响应时间线性增长，可能导致OOM
解决方案:
  - 使用 Spring Data 的 Pageable 参数实现分页
  - 统计类接口使用 COUNT/SUM 聚合查询替代全表加载
  - 技术: Spring Data JPA Pageable, @Query with COUNT/SUM

问题 1.2: N+1 查询问题（已优化：Booking/HotelBooking/评论等列表关联改为LAZY，并在列表查询上补充@EntityGraph加载必要关联）
------------------------------------------------------------------------
位置: Booking.java, BookingController.java
现象: Booking 实体的 @ManyToOne 关联(User, ScenicSpot)默认 EAGER 加载，
      查询列表时每条记录触发额外SQL
解决方案:
  - 将关联改为 FetchType.LAZY
  - 列表查询使用 @EntityGraph 或 JOIN FETCH
  - 技术: JPA @EntityGraph, JPQL JOIN FETCH, FetchType.LAZY

问题 1.3: 缓存未充分利用（部分优化：新闻分页列表接入Spring Cache并在后台资讯变更时清理缓存；景点列表因当前本地化逻辑会原地改对象，暂不缓存以免语言串写）
------------------------------------------------------------------------
位置: 各 Service 层
现象: 项目已配置 Redis 缓存基础设施，但读多写少的接口(景点列表、新闻列表)
      未使用 @Cacheable 注解
解决方案:
  - 景点列表、热门景点、新闻列表添加 @Cacheable
  - 数据变更时使用 @CacheEvict 清除
  - 利用已引入的 Caffeine 做本地一级缓存(L1)，Redis 做二级缓存(L2)
  - 技术: Spring Cache @Cacheable/@CacheEvict, Caffeine L1 + Redis L2 多级缓存

问题 1.4: AI路线生成接口同步阻塞（已核对：项目已有WebClient流式SSE接口/api/routes/generate/stream；同步接口仍作为兼容入口保留，本轮未改成任务轮询）
------------------------------------------------------------------------
位置: AiRouteController.java
现象: 调用外部AI API时同步等待，占用Servlet线程
解决方案:
  - 使用 @Async 或 CompletableFuture 异步处理
  - 或改用 WebClient (响应式非阻塞HTTP客户端)
  - 前端轮询或 SSE 获取结果
  - 技术: Spring @Async, WebClient, Server-Sent Events (SSE)

2. 安全加固
================================================================================

问题 2.1: CSRF 防护被禁用（已核对：Spring Security内置CSRF仍关闭，但Cookie JWT已配SameSite=Strict且已有CsrfCookieFilter校验XSRF-TOKEN；本轮未切换到Spring内置CSRF）
------------------------------------------------------------------------
位置: SecurityConfig.java
现象: csrf().disable() 全局禁用CSRF保护
风险: 如果使用Cookie存储JWT，存在CSRF攻击风险
解决方案:
  - 若JWT存于localStorage: 当前配置可接受，但需确认前端实现
  - 若JWT存于Cookie: 必须启用CSRF保护或使用SameSite=Strict
  - 推荐: 对状态变更接口(POST/PUT/DELETE)启用CSRF Token
  - 技术: Spring Security CsrfTokenRepository, SameSite Cookie属性

问题 2.2: CORS配置与前端不一致（已优化：后端CORS改为allowCredentials(true)，默认开发源改为明确localhost/127.0.0.1列表，生产仍通过CORS_ALLOWED_ORIGINS显式配置；本地安全复查中又忽略精确*通配源，避免凭证模式被误配成任意来源可访问）
------------------------------------------------------------------------
位置: WebMvcConfig.java
现象: allowCredentials(false) 但前端 Axios 配置了 withCredentials: true
风险: 跨域请求携带凭证时浏览器会拒绝响应
解决方案:
  - 统一配置: 若需要携带Cookie则设 allowCredentials(true)
  - 同时将 allowedOrigins("*") 改为具体域名列表
  - 技术: Spring CORS Configuration, 指定 allowedOriginPatterns

问题 2.3: 缺少接口限流（不完全准确：当前已有RequestRateLimitFilter，对登录/注册/AI/上传/后台接口做基础限流；本地安全复查中补充登录IP记录默认不信任X-Forwarded-For，避免请求头伪造污染用户登录信息；本轮未升级为Redis分布式限流）
------------------------------------------------------------------------
位置: 全局
现象: 无任何限流机制，登录、注册、AI生成等接口可被暴力攻击
解决方案:
  - 使用 Redis + 自定义注解实现接口限流
  - 或引入 Bucket4j / Resilience4j RateLimiter
  - 登录接口: 同一IP 5次/分钟
  - AI生成接口: 同一用户 10次/小时
  - 技术: Bucket4j, Resilience4j, Redis Lua脚本限流

问题 2.4: 输入验证不完整（部分优化：登录/注册/AI等已有@Valid；本地安全复查中将景点门票预订从Map改为BookingRequest DTO，补充酒店预订姓名/电话/备注长度与格式校验并入库前转义；仍有部分后台Map入参可继续DTO化）
------------------------------------------------------------------------
位置: 多个Controller的请求DTO
现象: 部分DTO缺少 @Valid 注解和字段约束
解决方案:
  - 所有接收用户输入的DTO添加 Jakarta Validation 注解
  - Controller方法参数添加 @Valid
  - 全局异常处理器统一返回校验错误信息
  - 技术: Jakarta Bean Validation (@NotBlank, @Size, @Email, @Pattern)

问题 2.5: JPA ddl-auto: update 用于生产环境（已优化：application-prod.yml改为ddl-auto: validate，并引入Flyway及索引迁移脚本；开发/本地环境保留update）
------------------------------------------------------------------------
位置: application.yml / application-prod.yml
现象: 使用 ddl-auto: update 自动修改生产数据库表结构
风险: 可能导致数据丢失、不可控的Schema变更
解决方案:
  - 生产环境设置 ddl-auto: validate (仅校验不修改)
  - 引入 Flyway 管理数据库版本迁移
  - 技术: Flyway, ddl-auto: validate

问题 2.6: 本地攻防视角复查出的轻量安全问题（已优化：按“本地项目/演示环境”威胁模型处理，不做过度公网加固）
------------------------------------------------------------------------
位置: BookingController.java, HotelBookingService.java, AdminController.java, WebMvcConfig.java, IpLocationService.java
发现与处理:
  - 异常输入可让景点门票预订Map解析抛500（已优化：新增BookingRequest DTO并使用@Valid，缺失/越界/过去日期返回400）
  - 酒店预订的入住人、电话、备注可直接入库（已优化：补充DTO字段约束，并在Service层使用InputSanitizer转义/限长）
  - 普通管理员可调整其他管理员角色或误操作超级管理员角色（已优化：超级管理员角色不可改，管理员角色变更仅超级管理员可执行，且禁止取消自己的管理员权限）
  - CORS若手滑配置为*且携带凭证存在误暴露风险（已优化：精确*通配源会被忽略并记录警告）
  - 登录IP默认信任X-Forwarded-For可被本地请求伪造（已优化：默认只用remoteAddr，只有显式TRUST_PROXY_HEADERS=true才信任代理头）

3. 架构改进
================================================================================

问题 3.1: AdminController 违反单一职责原则（确认正确，暂未执行：这是大规模接口拆分，需配合前端与回归测试单独做；本轮先完成分页和查询层优化）
------------------------------------------------------------------------
位置: AdminController.java (1498行, 20+注入依赖)
现象: 一个Controller承担了用户管理、景点管理、新闻管理、酒店管理、
      统计分析等所有后台功能
解决方案:
  - 拆分为多个Controller: AdminUserController, AdminSpotController,
    AdminNewsController, AdminHotelController, AdminStatsController
  - 业务逻辑下沉到对应Service层
  - 技术: 控制器拆分, Service层重构

问题 3.2: Controller直接调用Repository（确认正确，暂未执行：AdminController仍直接调用Repository；建议后续和3.1一起迁移到Service层）
------------------------------------------------------------------------
位置: AdminController.java, 部分其他Controller
现象: Controller直接注入Repository执行数据库操作，跳过Service层
风险: 业务逻辑分散，难以复用和测试
解决方案:
  - 所有数据访问通过Service层
  - Controller仅负责参数接收、调用Service、返回响应
  - 技术: 分层架构重构

问题 3.3: 缺少统一异常处理（不完全准确：当前已有ApiExceptionHandler统一处理校验、权限、上传和通用异常；响应格式仍主要是{error}，未改为{code,message,data}）
------------------------------------------------------------------------
位置: 全局
现象: 各Controller自行try-catch，错误响应格式不统一
解决方案:
  - 创建 @RestControllerAdvice 全局异常处理器
  - 定义统一错误响应格式 {code, message, data}
  - 自定义业务异常类(BusinessException)
  - 技术: @RestControllerAdvice, @ExceptionHandler

4. 数据库优化
================================================================================

问题 4.1: 缺少数据库索引（已优化：按当前真实列名添加JPA索引和Flyway迁移，覆盖bookings、hotel_bookings、shared_routes、travel_questions、route_comments、comment_likes等高频查询）
------------------------------------------------------------------------
位置: 多个实体类
现象: 高频查询字段缺少索引
需要添加索引的字段:
  - Booking: user_id, scenic_spot_id, booking_date
  - SharedRoute: user_id, created_at
  - TravelQuestion: user_id, created_at
  - RouteComment: route_id, user_id
  - CommentLike: comment_id, user_id (联合唯一索引)
解决方案:
  - 使用 @Table(indexes = {...}) 或 Flyway 迁移脚本添加索引
  - 技术: JPA @Index, Flyway migration SQL

问题 4.2: 连接池未优化（不完全准确：当前application.yml/application-prod.yml已有Hikari maximum-pool-size、minimum-idle、timeout、lifetime等配置；本轮未再调整）
------------------------------------------------------------------------
位置: application.yml
现象: 使用HikariCP默认配置，未根据业务调优
解决方案:
  - 设置合理的连接池参数:
    maximum-pool-size: 20 (根据并发量调整)
    minimum-idle: 5
    connection-timeout: 30000
    idle-timeout: 600000
    max-lifetime: 1800000
  - 技术: HikariCP配置优化

问题 4.3: 缺少慢SQL监控（部分优化：已配置Hibernate慢SQL阈值HIBERNATE_SLOW_QUERY_MS并开启org.hibernate.SQL_SLOW日志；生产MySQL slow_query_log仍需在数据库侧单独开启）
------------------------------------------------------------------------
位置: application.yml
现象: 未开启慢查询日志
解决方案:
  - 开启 Hibernate SQL日志(开发环境)
  - 配置 MySQL 慢查询日志(生产环境)
  - 引入 p6spy 或 datasource-proxy 监控SQL执行时间
  - 技术: p6spy, MySQL slow_query_log

5. 前端优化
================================================================================

问题 5.1: Axios全局超时设置过长（已优化：Axios默认超时改为15秒，AI生成保留180秒，上传保留60秒）
------------------------------------------------------------------------
位置: frontend/src/api/index.ts
现象: timeout: 180000 (3分钟) 全局超时
风险: 用户体验差，长时间无响应
解决方案:
  - 普通接口超时设为 10-15秒
  - 文件上传/AI生成等特殊接口单独设置较长超时
  - 技术: Axios instance per-request timeout override

问题 5.2: 缺少请求去重和缓存（已优化：Axios GET请求增加并发去重和15秒短缓存，非GET变更后自动清理缓存）
------------------------------------------------------------------------
位置: frontend/src/api/index.ts
现象: 相同请求可能被重复发送(如快速点击)
解决方案:
  - 实现请求去重(相同URL+参数的并发请求只发一次)
  - 对GET请求添加短时缓存(SWR策略)
  - 技术: Axios CancelToken/AbortController, @tanstack/vue-query (SWR)

问题 5.3: 路由级代码分割不彻底（不完全准确：当前路由已全部使用动态import，Vite也已有manualChunks；本轮仅验证未改动）
------------------------------------------------------------------------
位置: frontend/src/router/
现象: 部分路由组件可能未使用动态import懒加载
解决方案:
  - 确保所有路由使用 () => import('...') 懒加载
  - 大型第三方库(地图、图表)使用动态import
  - 技术: Vue Router lazy loading, Vite dynamic import, manualChunks

问题 5.4: 图片资源未优化（确认正确，暂未执行：需要图片资产压缩、缩略图生成和CDN策略专项处理）
------------------------------------------------------------------------
位置: frontend/src/assets/, 用户上传图片
现象: 图片未压缩、未使用现代格式、无懒加载
解决方案:
  - 静态图片使用 WebP/AVIF 格式
  - 列表页图片使用 loading="lazy"
  - 后端上传时生成缩略图
  - 使用CDN加速静态资源
  - 技术: vite-plugin-imagemin, <img loading="lazy">, sharp(后端缩略图)

问题 5.5: 缺少前端错误监控（部分优化：已添加Vue全局errorHandler、window error/unhandledrejection捕获，并支持VITE_FRONTEND_ERROR_REPORT_URL上报；Sentry等第三方DSN未接入）
------------------------------------------------------------------------
位置: 全局
现象: 前端异常无上报机制
解决方案:
  - 接入 Sentry 前端错误监控
  - Vue全局错误处理器 app.config.errorHandler
  - 技术: @sentry/vue, Vue errorHandler

6. 部署与运维优化
================================================================================

问题 6.1: Docker镜像未优化（已优化：后端Dockerfile增加依赖缓存层、非root用户运行和JVM容器参数JAVA_TOOL_OPTIONS）
------------------------------------------------------------------------
位置: backend/Dockerfile
现象:
  - 未使用多阶段构建的依赖缓存层
  - 容器以root用户运行
  - 未设置JVM内存参数
解决方案:
  - 分离依赖下载和代码编译阶段(利用Docker层缓存)
  - 添加非root用户运行
  - 设置JVM参数: -XX:MaxRAMPercentage=75.0 -XX:+UseG1GC
  - 技术: Docker multi-stage build, JVM容器化参数

问题 6.2: Docker Compose缺少资源限制（已优化：docker-compose.yml和docker-compose.prod.yml为backend/frontend/redis添加CPU与内存限制）
------------------------------------------------------------------------
位置: docker-compose.yml, docker-compose.prod.yml
现象: 服务未设置内存和CPU限制
风险: 单个服务内存泄漏可能拖垮整个主机
解决方案:
  - 为每个服务设置 deploy.resources.limits
  - backend: memory 1G, cpus 1.0
  - frontend: memory 256M, cpus 0.5
  - redis: memory 512M, cpus 0.5
  - mysql: memory 1G, cpus 1.0
  - 技术: Docker Compose deploy.resources

问题 6.3: 健康检查不规范（已优化：引入Actuator，放行/actuator/health，并将Compose健康检查改为/actuator/health/readiness）
------------------------------------------------------------------------
位置: docker-compose.yml
现象: 后端健康检查使用业务接口 /api/spots 而非专用健康端点
解决方案:
  - 引入 spring-boot-starter-actuator
  - 使用 /actuator/health 作为健康检查端点
  - 配置 liveness 和 readiness 探针
  - 技术: Spring Boot Actuator, Docker HEALTHCHECK

问题 6.4: 缺少日志收集方案（部分优化：生产Logback改为JSON控制台+滚动文件日志，并输出application/traceId/spanId；ELK/Loki等集中采集仍需后续接入）
------------------------------------------------------------------------
位置: 全局
现象: 日志仅输出到容器stdout，无持久化和集中管理
解决方案:
  - 配置日志输出为JSON格式
  - 使用 Docker logging driver 或 ELK/Loki 收集
  - 技术: Logback JSON encoder, Grafana Loki / ELK Stack
