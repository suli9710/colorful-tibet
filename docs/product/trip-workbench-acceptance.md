# 西藏行程工作台：实现范围与上线验收

## 产品边界

本工作台帮助用户发现行程中的不确定信息、修改安排、保存行前清单，不是医疗评估、实时导航或已接通全部供应商的旅行交易平台。

- 生成、缓存、备用路线和手工修改使用相同产品约束。规则通过也不意味着医学安全或已经核验可执行。
- 房型可住人数与库存间数分开。旧数据的库存默认未知，运营人员必须核对后填写；不能把既有房型资料当成有房。
- 价格是参考估计，库存是本系统管理的数量，二者均不证明外部供应商已确认。支付、退款和咨询状态必须分别表达。
- 来源入口、作者自述、个人准备勾选和平台核验是不同概念。未逐项核验的信息不显示“已核验”。
- 公开分享会最小化常见直接标识及显式私人字段，但自由文本过滤不保证匿名，发布前仍需用户复核。离线包采用允许字段投影，不导出订单个人资料。

## 工程验收矩阵

| 维度 | 必须覆盖的场景 | 证据要求 |
| --- | --- | --- |
| 行程规则 | 日期/天数/重复天号、时间冲突、未知人数、住宿匹配、容量、库存、旧规则版本、高海拔住宿产品阈值 | 固定回归样例；生成/读取/编辑一致，未知不改成确定 |
| 订单与库存 | 两个用户并发争抢最后库存、逐夜占用、多个数量、旧订单镜像去重、到期释放、晚确认 | 单元回归 + 真正 MySQL 事务并发测试，不能以 mock 证明锁正确 |
| 授权与隐私 | 非所有者读取/修改行程和订单、管理员库存权限、公开分享脱敏、离线 HTML 注入 | 服务/控制器/组件回归，输出不包含非必要订单或健康字段 |
| 可信表达 | 估价/未知库存/咨询/模拟支付/人工退款分别显示 | API 契约及关键 UI 文案回归 |
| 易用性 | 逐日切换、修改时间、冲突解释、取消修改、准备清单、导出、重复操作 | 组件回归；360–430px 真浏览器与键盘验收单列 |

| 数据迁移 | 原有订单保持、库存未知、历史人数/规则未知、作者自述不追认认证 | MySQL Flyway + JPA context；旧数据回归 |

## 真实供应商 / 付款上线闸门

下列依赖没有完成前，不开放承诺供应商确认的生产收款闭环：

1. 确定有资质的履约方、库存数据责任人、更新频率及异常联系方式。
2. 核验报价有效期、费用包含/不含、退改条款及渠道身份；过期或未知必须降级显示。
3. 真实支付渠道回调、签名、金额、幂等、退款回执和对账经过独立验收；模拟渠道与人工记账不能代替。
4. 在真实 MySQL 环境运行并发库存测试；确认迁移、回滚计划与已有预订保持。多房型订单和确认/取消竞争仍可能触发数据库死锁回滚，需压测并定义安全重试行为，不能将单元测试等同于生产并发证明。
5. 明确客服和申诉处理责任、内容许可及隐私处理流程。

这些工作不能通过生成虚构供应商记录、示例订单或“已验证”标签完成。

## 内容维护与用户验证（外部依赖）

- 首批20–30个常用景点/活动需逐条由内容维护人核验，记录原始官方链接、适用日期、核验时间、负责人和到期处理。当前参考入口不冒充完成此项。
- 预约、证件、道路、海拔及健康相关资料须按具体日期/人群核对；不把边境证等不同手续混成单一资格判断。
- 文化内容需有作者、授权与本地校订；“已走过”和旅行月份是自述，点赞不证明事实。
- 8–12位目标用户任务观察和20–30位自愿试用需要实际招募同意。首轮观察修改一天、找到预约入口、理解总价、处理冲突、导出5项任务。
- 记录“准备完成率”，只有经用户自愿回访确认实际采用后才计算“实际采用比例”。不采集不必要的健康史、证件或联系方式作为分析事件。
- CWV目标：真实用户p75 LCP≤2.5秒、INP≤200毫秒、CLS≤0.1；没有真实样本不得宣称达标。

## 保持克制

本阶段不迁移技术栈，不建设全国OTA或全网最低价承诺，不添加未经许可的第三方追踪，不部署、不发起真实交易。工程交付、CI通过、内容核验、用户研究和生产履约是五个独立完成状态。
