# 旅游规划界面竞品观察

调研日期：2026-11-01。用于本项目本轮 UI 与操作流程设计；不复制竞品品牌、素材或整套界面。

## 方法与边界

通过独立浏览器会话实际访问官方页面，截图后逐张查看。桌面视口为 1440 × 1000，窄屏视口为 390 × 844。窄屏使用桌面浏览器调整视口，不等同于真实手机或竞品原生 App 测试。没有登录、创建旅行、发出邀请或完成交易；登录后编辑、价格有效性、保存与同步结果均未验证。

本轮有效参考为 **Wanderlog、Trip.com / Trip.Planner、TripIt** 三家。Klook 遇到 DataDome 验证页，未绕过，不能据此评价其产品界面。

## 1. Wanderlog：先开始，再逐步补充

来源：[官网首页](https://wanderlog.com/)；[创建行程](https://wanderlog.com/plan/create)。首页展示的是官方产品示意画面，创建行程为真实可交互页面。

已观察：

- 首页以一个主要规划入口和一个较弱的下载入口建立层级；官方产品画面把行程清单与地图并列，预算、预订各有明确区域。不能从该画面推断实际保存或地图同步已通过测试。
- 创建页以目的地为第一项，日期明确标为可选；邀请旅伴是附加操作，主按钮为“开始规划”，另一个撰写指南入口降为文字样式。表单没有重复堆叠功能介绍。
- 在 390px 下，目的地、日期和主操作保持单列可见。顶部导航收拢，主要表单不产生横向滚动。
- 实际点击空目的地的“开始规划”后，错误在目的地字段下显示，表单留在原位；日期与旅伴控件仍可继续操作。未验证输入有效目的地后的服务端行为。

可取做法：首次规划只要求必要偏好；常用预设帮助快速起步；错误紧邻字段；结果以每日任务和预算区域组织。保留本项目已有天数、预算、偏好功能，不照搬其颜色与布局。

证据：[桌面首页](verification/ui-flow/competitors/wanderlog-desktop.png)、[桌面创建页](verification/ui-flow/competitors/wanderlog-start.png)、[窄屏创建页](verification/ui-flow/competitors/wanderlog-start-mobile.png)、[窄屏校验反馈](verification/ui-flow/competitors/wanderlog-validation-mobile.png)。

## 2. Trip.com / Trip.Planner：集中输入，区分任务

来源：[首页](https://www.trip.com/)（本次自动跳转至[香港站](https://hk.trip.com/?locale=zh-hk)）；[Trip.Planner](https://hk.trip.com/webapp/tripmap/tripplanner?source=t_online_homepage&locale=zh-HK&curr=HKD)。

已观察：

- 首页左侧提供完整产品导航；中央搜索区按住宿、机票等任务切换。目的地、日期、房客数量和搜索按钮集中在一个区域，默认日期与人数直接可见。
- 首页同时有优惠卡、登录提示与浮动助手，信息密度较高。对本项目而言，适合借鉴字段组织，不宜复制所有营销入口。
- Trip.Planner 把目的地、日期/天数、偏好收在一个面板，分别提供自行建立和 AI 规划入口。下方“我的行程”区域说明登录后才能查看，并提供登录动作。
- 桌面右侧地图区域在本次访问中未成功显示地图底图，不能宣称地图联动已验证。窄屏重新加载后仍观察到横向溢出，部分操作在可见区域外；不能把这次桌面 UA 的表现推断为其手机 App 体验。

可取做法：规划输入、生成动作、已有行程分层呈现；登录要求在需要保存/查看时说明；日期与数量默认值要显式展示。避免复制大面积空地图和窄屏溢出的布局。

证据：[桌面首页](verification/ui-flow/competitors/trip-desktop.png)、[桌面规划页](verification/ui-flow/competitors/trip-planner.png)、[窄屏规划页](verification/ui-flow/competitors/trip-planner-mobile.png)。

## 3. TripIt：让用户理解流程与数据来源

来源：[官网首页](https://www.tripit.com/web)；[官方使用流程](https://www.tripit.com/web/free/how-it-works)。这部分为真实官网的产品说明页和官方示意图，不是登录后的旅行编辑器。

已观察：

- 导航将产品、使用方法和价格分开；当前使用方法页面有明确选中状态。
- 使用说明把流程拆为三个动作：转发预订确认邮件、汇成行程、在设备上查看。每段只有一个清晰标题和相关下一步，避免把所有能力挤进一个大表单。
- 官网明确说明整理的是用户已有预订资料；行程汇总与购买预订是不同的任务。这为本项目区分“生成建议”“参考预算”“实际预订”提供信息结构参考，不意味着本项目已有邮件导入能力。
- 390px 下导航变为菜单按钮，图文从左右排布变为纵向，正文和主操作保持可见。未操作登录表单，未验证错误、成功、离线同步与真实通知。

可取做法：用短步骤说明“规划 → 调整 → 核对 → 保存/导出”；预算和待确认事项跟随结果出现；保存与导出旁说明其含义，避免把文件生成暗示成订单完成。

证据：[桌面使用流程](verification/ui-flow/competitors/tripit-how-it-works.png)、[流程详情](verification/ui-flow/competitors/tripit-detail.png)、[窄屏使用流程](verification/ui-flow/competitors/tripit-how-mobile.png)。

## 对七彩西藏的设计决策

| 用户任务 | 本轮采用 | 不据此作出的承诺 |
| --- | --- | --- |
| 开始规划 | 清晰主操作、紧凑偏好、常用天数预设、空态步骤提示 | 不增加没有接口支持的目的地筛选或实时库存 |
| 阅读与调整 | 每日行程优先，概览与全文层级分开，避免重复内容占据首屏 | AI 建议不等于路线已核实可行 |
| 核对预算 | 预算旁直接注明参考性质，保留开放时间、路况与预订待确认提示 | 不宣称参考价格实时、库存充足或可以直接预订 |
| 保存与导出 | 在结果附近说明下一步、登录条件与数据保留范围 | 下载文件不代表云端保存或订单确认 |
| 小屏与失败恢复 | 单列重排、字段邻近提示、清晰重试、保留已有输入 | 竞品未验证的成功/离线流程不视为本项目能力 |

视觉方向：保留本项目藏红、山水蓝、暖纸色与中文标题气质；降低重复纹样、渐变、半透明小卡的密度；统一边框、控件高度、文字层级和焦点状态。以真实界面和本地流程验证决定最终实现，不把竞品截图当作本项目效果证明。
